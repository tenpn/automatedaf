An actionable failure is one that helps you get to the crux of the matter quickly. You don't want to have to load up the test to see what it was actually asserting, or go scrub a log, just so you can do the fix.

How do you write tests so they'll be actionable?

📛Informative test name

"ChecksWorking" is a really bad test name! You want a good idea from the test of what's being tested and how it's being tested. That means specifics, and that means long test names, and that's fine.

Even once you've got a long test name, you want to be very literal. HighScore_OnFirstBoot_IsInvalid is still not great - what does "is invalid" mean here? Is it returning null for a high score? Is it returning -1? HighScore_OnFirstBoot_IsMinus1 is much better.

Now if you see that fail, and you know the code, you might have a good chance of jumping straight to the bug.

🫥Full picture

Sometimes the name is enough but sometimes you want to see the details. Your test should be readable so that you can easily tell how the test sets up the context and what it does with the results.

One of the most common ways for new testers to get this wrong is by putting multiple asserts in a test. I get why this is attractive: if an existing test works exactly as you expect already, it's really tempting to just slip in another assert to test a different bit of state.

However most test frameworks will stop running a test after the first failure, so you don't get the full picture on what's working. If the _second_ assert would have given more context on the broken code, but it never ran, then you're not getting the full picture.

It's ok to copy-paste your tests, at least to begin with. Then you can lean on fixtures to share setup/teardown code, as well as custom helper functions, to make it easy to bootstrap new tests in your library and get the full picture on every run.

⬆️Surfaced errors

If a test claims a failure, it should show the appropriate error along with it. This is especially important for things like smoke tests, that might fail on unknown log errors. Use Jenkins' Build Failure Analyzer plugin, or Teamcity's failOnText to capture potential log problems to the top level.

If you're posting a failure to slack or some other chat app, make sure the failures go with it too. Don't make people click through unless there's a really strong reason to - they should be able to diagnose the whole problem from just the slack post.
