There's an old adage that bugs cost 100x more to fix in production than in development. The actual numbers are probably folklore, but the core of it rings true.

Why are old bugs expensive?

One of the biggest reasons is that if you're three months out from working on this system, you'll have to take some time to refamiliarise yourself. The fix could be one line, but it'll take you an hour to figure out what that one line is. If you had tackled this bug on the same day you created it, you may have been able to instantly identify the line.

Even if you can get back in the headspace of the problem, the real fix could now be much more complicated. The system will have matured, and other systems will have grown up around it. What might have originally been changing the behaviour of one method used in one place, is now a much more complicated refactor.

And that's only counting the cost of fixing - there's also a small-but-accumulating cost every day the bug lives in the codebase. People have to avoid or mitigate the bug in ways that rapidly add up.

Why doesn't everyone fix bugs early?

There's really only two reasons: The first is, that they don't want to. They know about the bug but they don't prioritise fixing. There's systemic reasons, especially in game dev, but if you have any agency over this, please re-read the paragraphs above and change your ways!

The second reason, the one I can help with, is that they don't know about the bug yet.

Maybe the team has limited testing resources: not enough testing hours for each milestone.

It could be that the feature isn't super easy to test, requiring complex setup or precise input timings.

Possibly the QA team didn't know to test the feature, because they didn't know it had changed.

Finally, it could be that the bug manifests easily, but detecting it is hard. Imagine a UI bug that causes poor UX but could pass for as-designed.

Automation helps with all of this

If your testing resources are limited, why waste them on monotonous repetitive tests that machines can do just as well?

Because programmers are naturally impatient, when they make automated tests they'll make them fast. No more long precise input sequences required.

If communication is a problem, you should still solve that, but the QA team don't need to know that new tests shipped. They ship and they run.

And lastly, automated tests don't deal in ambiguity. If the system is not working as designed, they'll fail. There'll be no manual interpretation to get wrong.

So we can see the true purpose of automation is as a tool for catching bugs faster.

Which we know now actually makes it a tool for saving money and time.

Can you afford not to use test automation?
