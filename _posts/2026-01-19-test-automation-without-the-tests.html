I've been interested recently in the leap between "we've got a build server" and "we have test automation".

People might be excited by the idea of the server testing the game for you, but put off by finding the right framework, or skilling up, or hiring the right skillset.

Of course, I can help with those problems, but there are things you can do, using the tools you already know, to gain some of the safety of test automation without writing any tests.

For instance, let's take shader errors in Unity. They're easy to do, especially when it comes to platform-specific code, and it could take QA a while to hunt down the single small purple triangle in a real build. And as we all know, the longer between bug creation and detection, the more expensive the fix is!

Unity will continue to happily spit out a build if there's a shader error, but it will log the error to the console. Your build server could do a simple regex scan of the log, find the exact error, fail the build, and post it to slack. This takes no specific test framework or new skillset, and you're now able to catch shader errors earlier and fix them faster.

There's many examples of this, not just log scanning but things like:
- Turning on warnings as errors
- Static analysis
- A simple does-the-game-boot-without-errors smoketest

You could even imagine tracking stats like build time, build size, asset import time, or individual asset size, and producing alerts directly from the build script if they pass some threshold. This isn't even that complicated - some lines of bash or powershell, a few bits of regex - but the range of issues and defects you can find through it is numerous.

If you're having trouble getting the code team to commit to integrating the right automation SDK, maybe you can instead start doing some of these framework-less "tests", demonstrate the benefit over a few release cycles, and get some buy-in.
