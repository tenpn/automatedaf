--- layout: post title: "What's worse, false positive or false negative tests?" date: 2026-06-23 19:17:47 +0000 categories: [Test Automation] newsletter: true newsletter_id: 191092678726780281 ---

Tests can start to go wrong in lots of ways, but two of the most common are false positive and false negative. What's the difference, and which is more insidious?

False Positives

These tests can fail while the behaviour they're testing for is still working. (It feels unintuitive to some to call failures "positive", but a failing test is being assertive (literally, I guess?) and giving information, so it's called Positive)

This can happen because the test is buggy. Most simply, the assert can just be backwards, testing for true instead of false. This is why I always prefer var == false over !var, the latter is much more subtle!

The test could also be correctly written, but depends on a second behaviour to work, and that behaviour is broken. That second behaviour might come from a completely separate system that you're using to keep test admin to a minimum.

As long as your test does still actually fail when the behaviour under test is broken, then your test still has some value. If it only fails when other systems break, then you've got a genuine problem to fix.

Sometimes false positives are the cost of doing business. Although it would be wonderful if we lived in a world where one bug causes exactly one test failure, real life intrudes. Sometimes it's impractical to eliminate all dependencies, and there's value still in having tests that can be prone to false positives.

Often, with familiarity with a system, it's easy to identify the One True Failure under a cascade of false positives - if System B depends on System A, and both A and B tests are failing, you should look at the A tests first.

However you should keep an eye on things. If there's some tests that are prone to failing all the time, you might want to look more closely at how you can isolate them. It can be draining to trawl through hundreds of failures to find the real problem.

False Negatives

False negatives pass when the behaviour they're testing is actually broken. As you can imagine, the absence of information is much harder to keep an eye on.

A suite of false negatives can give you false confidence that the system is working when it's actually super buggy. All that work writing, maintaining and executing the tests is providing absolutely no value. This makes false negatives a much bigger threat than false positives.

More often than not this is a broken test. Maybe it's accidentally running against test functionality, not production code, or it's misconfigured its dependency injection. Or it's just a simple logic bug!

The best way to prevent false positives is to test your tests - you should always make sure you see a new test failing against broken production code.

That could be because you are doing Test Driven Development and so writing the failing test before creating the code in the first place. Or maybe you're doing a regression test against a bug, and can easily revert your fix to test.

But if you're testing behaviour that's not broken, it's beholden on you to fuzz it in such a way that you see your test fail.

In fact, I'd go as far to say that no test should get pushed live until you've seen it fail once!
