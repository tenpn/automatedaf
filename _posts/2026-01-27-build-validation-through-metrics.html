A few weeks ago we were talking about the gap between "we've got a build server" and "we have test automation".

One option we discussed then was log scanning for common problems, rather than writing a formal test in a test framework. Today I wanted to discuss another approach: build validation through metrics.

One really simple thing most people can do today is fail the build if the build size passes some agreed-upon threshold. There's nothing worse than reaching the end of dev and discovering you need to trim 500mb to fit in download limits! Again, this requires no SDK integration into the build nor training in test frameworks.

This is effective but pretty crude - you might have to do some digging to find out who broke the camel's back. You could also alert based on a large jump in build size compared with the previous build, but even better is a stats dashboard like grafana, which can be free to self-host. TeamCity even has time-series graphing built-in!

Other stats that might be useful to track include:

- Single largest asset
- Compile time
- Cook/build time
- Time to boot to main menu, if you have simple smoke testing
- Performance metrics

And while it's bad if any of these stats jump, track if they suddenly fall too - if your main menu boot time is suddenly milliseconds, that's a sign that something's gone wrong with the build!

Happy testing!
